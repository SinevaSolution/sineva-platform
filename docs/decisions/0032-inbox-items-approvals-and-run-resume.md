# ADR-0032: Inbox items, approvals and run resume

## Status

Accepted (2026-10-22). Founder delegated: the implementation plan's ADR backlog names the recommended options (X-09 approvals, X-11 pause and resume, P-28 inbox data model) and the Founder delegated their acceptance to the work package that builds them (WP-M1-40). The sineva-ai half of the contract (the `approval_required` and `input_required` events, the resume endpoint) is proposed here by the platform and is pending the sineva-ai team (WP-M1-07). It is built against fixtures and a fake upstream until then.

## Context

A specialist that wants to do something a person must approve, or that is blocked on an answer, has to appear in one place (the Inbox) and the paused run has to continue with the outcome. In M1 the only approval type is `draft.review`: approving marks a draft ready and executes nothing. M2 adds executing action types without changing the item model. Other features will create items too (mentions, escalations, Customer chats), so creation must be a port, not a chat-specific path.

## Decision

1. **Ownership.** The platform owns `inbox_items`, `inbox_item_reads`, `approvals`, `approval_revisions` and `input_requests` (schema `platform`, UUID keys generated by the database). sineva-ai only produces events.
2. **Item model.** `inbox_items.kind` is `approval`, `input_request` or `result` in M1 (`handoff` and `system` arrive in WP-M2-13, `idea` in WP-M3-26). `state` is `open`, `resolved`, `dismissed` or `expired`. Tab mapping: approval and open goes to Needs review, input_request and open to Needs input, everything not open (and every `result`) to Done. `recipient_user_id` is the person whose chat produced the item; Member sees only their own, Owner and Admin see all, Viewer sees Done items as summaries without payloads (OQ-INBOX-5 default).
3. **Creation port.** `InboxItemCreator` (domain) takes a structured `NewInboxItem`. It is idempotent on `(workspace_id, dedupe_key)`; for approvals the key is the upstream approval id, for input requests the upstream request id. Chat approvals, system items and later mentions and escalations all go through it. The creator never accepts a user id from a request body: the recipient is derived from the platform run handle.
4. **Two producers, one result.** The relay creates the item when it sees `approval_required` or `input_required` in a run's stream and forwards a rewritten frame that carries only platform ids and no draft body. For runs with no attached browser (workflows, routines) sineva-ai calls `POST /internal/v1/approvals` and `POST /internal/v1/input-requests` (`X-Internal-Api-Key`, workspace validated, run handle resolved to the owner). Both are idempotent, so either order and replays are safe.
5. **Action-type registry.** `server/domain/approvals/action_types.ts` holds `draft.review` (risk low, reversible, `autonomy_eligible` false, `guardrail_locked` false, no execution, editable fields `title` and `body`). The "what will happen" sentence is a message key plus structured parameters built by the platform, never model text. An unregistered action type is refused with 422.
6. **Decisions.** `approve` (optionally with `edited_payload`, which becomes a revision, is validated against the registry and re-hashed), `reject` (optional note, stored, never shown to end customers), and ask for changes (instruction to the specialist; the approval stays pending with `awaiting_revision` until sineva-ai posts a higher revision under the same upstream id). The caller sends the `version` it saw. A decision is: (a) conditional claim of the row (status `pending`, matching version, version incremented, decider recorded); (b) the resume call to sineva-ai; (c) commit of the terminal state and the audit event in one transaction. If (b) fails the claim is released and the caller gets a typed 503 (502 for a bad answer); the item stays pending. The loser of a race at (a) gets 409 `already_decided` with the decider's name. Terminal states (`approved`, `rejected`, `expired`, `cancelled`) are immutable. A claim older than two minutes is released by the expiry job, which covers a crash between (a) and (c).
7. **Resume (proposed contract).** `POST {sineva-ai}/api/v2/runs/{upstream_run_id}/resume` with the signed context header, `X-Internal-Api-Key` and an `Idempotency-Key`. Body carries the kind, the upstream approval or input request id, the revision, the decision (`approved`, `rejected`, `changes_requested`, `expired`, `answered`, `dismissed`), the payload hash, and a `result` that for `draft.review` is always `{"executed": false}`. The plan text writes the path as `/internal/v1/runs/{run_id}/resume`; the `/api/v2/runs/...` form is used because every other sineva-ai run call (events, cancel) is there, and it is one constant to change.
8. **Expiry.** The job is `POST /internal/v1/inbox/expire` (internal key, no body), called by a scheduler because the platform has no job runner yet. Default 7 days, never later than a time named inside the payload by the action type, at most 30 days if the producer asks for longer. An internal job route runs the expiry use case: it marks pending items `expired`, never approves, resumes the run with `expired` ("not approved"), and retries a failed resume on the next run. It also reports approvals whose 24-hour reminder is due, for the notification work package.
9. **Session only.** Decision, changes and answer endpoints accept a Sineva session only. A bearer token that carries an audience claim (the shape MCP tokens will have) or the `mcp_` prefix is refused with 403. Sessions carry no `aud` today, so this is a stub that WP-M2-38 replaces with real audience checks; a test per route pins it.
10. **Permissions.** `inbox.view`, `approval.decide_own`, `approval.decide_any`, `inbox.answer` join the matrix. Member decides only items addressed to them. `approval.batch_decide` and `autonomy.update` are WP-M2-13.
11. **Audit.** `approval.requested`, `.approved`, `.edited`, `.rejected`, `.changes_requested`, `.expired`, `input.requested`, `input.answered`. Ids, counts and field names only, never draft text or answers.

## Consequences

- The `approvals.id` the browser holds is a platform UUID, not the sineva-ai id. The relay rewrites frames and the stored card `approval_id` so the two views read one record.
- A run that waits for a decision survives a closed tab (ADR-0022), and a failed resume is retryable by the user because the item stays pending.
- Two approvals of one run can be in flight; each has its own idempotency key.
- The 24-hour reminder and the email channel are not built here; the expiry job only reports them.
- Until sineva-ai ships WP-M1-07, only the fake upstream proves resume. The contract can still change; the fixtures are marked proposed.

## Alternatives considered

- **Commit then resume.** Simpler, but a failed resume leaves an approved item whose run never continues, and the user cannot retry. Rejected for the typed-503-stays-pending requirement.
- **Resume first, then commit with an optimistic check.** Two people could both resume the run, possibly with opposite decisions. The claim step removes that.
- **A separate `changes_requested` status.** The PRD status set has none; an `awaiting_revision` flag keeps the set and the item stays in Needs review.
- **Reuse the existing `sseApprovalRequiredEventSchema`.** Its shape (`action`, `parameters`) lacks the summary, expiry and guardrail reason the Inbox needs; the proposed schema is separate and the old one is left alone until sineva-ai confirms.
