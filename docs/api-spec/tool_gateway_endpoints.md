# Tool Gateway and Gmail execution

The platform implements the gateway and the four Gmail actions. The current chat runtime does not call it yet. This change does not edit `sineva-ai` or enable Gmail tools in chat. WP-M2-11 must wire the consumer, selected skill permissions and run suspend/resume; the platform must admit those scopes before minting the context. Existing chat calls receive no new tool permissions.

## Authentication and identity

Both routes require `X-Internal-Api-Key` and the original `X-Sineva-Context` minted by the platform. Session cookies, PATs and the cron bearer do not replace the internal key. The gateway verifies Ed25519 signature, issuer `sineva-platform`, audience `sineva-ai`, required timestamps, expiry, a lifetime of at most 60 seconds and a 16 KiB token cap. It requires bound workspace, user, specialist and run claims plus explicit `allowed_tools`, `skill_tools` and boolean `trifecta` flags. Missing tool scopes fail closed. `MintContextOptions.gateway` is a server-side admission interface; never populate it by copying model or browser input.

Every execution checks current account status, verified email, workspace membership, specialist scope and ownership of the run and conversation. A signed role cannot restore removed membership. The tool must appear in both signed tool lists; a skill cannot widen the specialist ceiling. SinoInsights cannot execute a write, and payment actions must remain reads. All non-read actions require a human approval, including every send under the trifecta flags. No autonomy setting can bypass that requirement in this implementation.

## POST `/api/internal/v1/tool-gateway/execute`

The `/internal/v1/tool-gateway/execute` alias has the same handler. Use the `/api` form on public hosts, since the page guard can redirect the other form.

```json
{
  "tool_name": "gmail_send_message",
  "arguments": {
    "to": ["person@example.test"],
    "subject": "Meeting follow-up",
    "body_text": "Thank you for the meeting."
  },
  "run_id": "run_33333333-3333-4333-8333-333333333333",
  "call_id": "call-1",
  "idempotency_key": "send-1",
  "mode": "live"
}
```

The request is strict: callers cannot add identity, credentials or an `approval_id`. Arguments are capped at 64 KiB and validated against the action registry. `mode` defaults to `live`; live writes require an idempotency key. The gateway resolves one visible connection granted to the signed specialist. Several eligible accounts produce `connection_ambiguous`; the gateway does not choose an account. An admin must narrow the specialist's grants to the intended account.

Successful envelopes contain a gateway outcome:

```json
{
  "status": "approval_required",
  "approval_id": "44444444-4444-4444-8444-444444444444",
  "error_code": "approval_required"
}
```

**Approval IDs have two purposes.** This `approval_id` is the runtime correlation ID, generated by the database for the gateway call and stored as `approvals.upstream_approval_id`. Inbox decisions use the separate platform approval row ID. The runtime must retain and emit the correlation ID unchanged; the platform maps it to the existing item. A correlated runtime event cannot replace the platform's sealed payload or create another Inbox item. Resume sends the same correlation ID.

An executed read or an approved action returns `status: ok`, a redacted `result`, and `error_code: null`. Results are marked `untrusted: true`. A replay can return the first stored `error` outcome. Policy and dependency failures use the standard error envelope and HTTP status, rather than a fabricated tool result.

### Gmail actions

| Action                  | Input                                                                       | Behavior                                                            |
| :---------------------- | :-------------------------------------------------------------------------- | :------------------------------------------------------------------ |
| `gmail_search_messages` | `query`, `max_results` (1 to 25, default 10)                                | Search IDs, then fetch message summaries in batches of at most five |
| `gmail_get_message`     | `message_id`                                                                | Fetch text from nested MIME parts; no attachments or active HTML    |
| `gmail_create_draft`    | `to`, optional `cc`, `subject`, `body_text`, optional `reply_to_message_id` | Create a Gmail draft after approval                                 |
| `gmail_send_message`    | Same as draft                                                               | Send after approval; irreversible                                   |

The adapter builds UTF-8 RFC email messages, rejects header injection and derives `From` from the connected account. A caller cannot choose a sender through arguments. Replies look up the provider's Message-ID and thread. When no plain-text body exists, the read uses the provider snippet and marks `body_source: snippet`; it does not claim to have returned the full message. HTML and remote images are never rendered by the approval preview.

The credential resolver is the only vault reader. The executor receives credentials only after permission, status, scope, rate and egress checks. Every network request uses the provider egress allowlist, timeout and streaming response cap. The gateway redacts credential patterns and exact resolved secrets before persisting or returning a result. Oversized reads return `truncated: true` with `response_truncated`; uncertain write results are errors, not success markers.

### Approval and idempotency

The gateway creates Inbox items for `email.search`, `email.read`, `email.draft.create` and `email.send`. The current connection grant default, `ask_every_time`, requires review for reads too. `ask_for_writes` permits admitted reads directly. Unknown policies fail closed for reads. Simulated writes return a platform-written preview without provider calls, credentials or approval creation; simulated reads still obey the stored read approval policy.

An approval seals the action, arguments, connection, external account and run. The existing session-only decision route claims the item, invokes the gateway, resumes the runtime with `executed: true`, then commits the decision. Draft review continues to send `executed: false`. The gateway rechecks permissions and the sealed hash before execution. Edits and change requests for the executing email payload are not supported in this slice; reject it and request a new review instead. The email preview shows the sender, recipients, subject and body. The UI waits for server confirmation before displaying Email sent. Viewer summaries omit the email subject and recipients.

`tool_gateway_calls` reserves each `(workspace, user, run, idempotency key)` and each call ID in Postgres. Only one claimant may invoke the provider. A completed result survives another instance or a resume retry. A changed payload or mode cannot reuse the key. Keys are hashed at rest; credentials and raw request arguments are absent from the call ledger (the approved payload lives in the Inbox).

A failure before provider invocation releases the reservation. An explicit provider refusal such as HTTP 401 or 429 also permits a retry of the same review. A timeout, write 5xx, invalid successful write response or lost execution outcome does not: the first failure stays recorded. A stale executing reservation becomes `tool_outcome_unknown` after 120 seconds and is never reclaimed for another send. An operator must check Gmail before starting a new review. No automatic retry can turn an uncertain send into a second email.

The admission event `connection.tool_called` is durable before provider invocation. A successful result and `connection.tool_completed` (result hash only) commit together. Denials and replay attempts emit `connection.tool_denied`. Audit metadata contains IDs, action names, mode and hashes, never email bodies, recipients or tokens.

## GET `/api/internal/v1/connections/resolve`

Query: `provider_id` and the signed `run_id`. The non-`/api` alias is also registered. The response contains granted connection IDs, provider IDs, status, access level and scope strings only. It returns no tokens, credential fields, secret versions or personal account labels.

## Limits and operations

`RedisToolCallLimiter` uses an atomic sliding window shared across instances and keyed by workspace and connection. Initial config: 30 calls per connection and 120 per workspace per 60 seconds. These are engineering safety limits, not plan entitlements or a measured production baseline. Redis failure returns `dependency_unavailable`; no in-memory allow-all fallback exists. The rest of WP-M2-07 (all route classes) remains separate.

Kill switches are queried on every call without an instance cache. Scopes: `provider`, `freeze`, `read_only`, `specialist`; `*` applies globally. The operator script and exact commands are in the [Connections runbook](../deployment/connections_runbook.md#7-tool-gateway-kill-switches). Owner/Admin controls remain M3 work.

Migrations: `20261023133000_tool_gateway_calls_and_kill_switches` and `20261023134000_tool_gateway_approval_binding`. They add tables and nullable binding columns; no existing data is removed. They have been exercised only on disposable test databases in this change, not the persistent local database or production.

## Verification and remaining work

The suites cover concurrent reservation and approved execution, process-independent replay, tenant and personal visibility, payload and account tampering, revoked grants, no unapproved send, rate sharing, an uncertain write, redaction, strict route bodies and session-only Inbox decisions. Fixtures in `src/__tests__/contract/tool_gateway_fixtures` are platform-owned and separate from the engine-owned chat fixtures. Copy them to the runtime when WP-M2-11 is undertaken.

Local measurement on 2026-10-22: seven write-admission samples against disposable Postgres, with a fake context verifier, audit logger and provider, gave median **16.86 ms**, range **11.18 to 38.69 ms**. This measures the admission/approval path only, excludes production signature/audit/network costs and is not a production latency claim.

Still required before Gmail works from chat: the runtime gateway client and tool registration, platform admission of the selected skill's signed scopes, run suspend/resume integration, and a live Google OAuth/provider journey. The current code deliberately does not infer skill scopes or grant new permissions to existing chat calls. Usage metering is WP-M2-34; general autonomy and batch approval are later work. If provider execution succeeds but runtime resume fails, the item remains pending and retry resumes using the stored gateway result. Resume delivery is not yet a durable outbox; expiry during a prolonged resume outage needs reconciliation against the call ledger.
